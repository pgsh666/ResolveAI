# 商城与电商客服验收

更新日期：2026-10-16。以下是复现步骤，不是随仓库发布的客户记录。优先在独立环境验收，勿向正在使用的业务数据库批量写测试数据。

## 准备

按[交付指南](DELIVERY.md)准备 Docker、私密管理员账号和语义模型。管理员使用商户后台，另一独立浏览器或无痕会话注册客户；普通标签共用 Cookie。

公开副本首次启动只有通用知识和本机自行生成的管理员，不生成预置工单、聊天、商品、订单、用户评价或模型调用记录。商户先上架自己的商品，再完成下面的流程。原开发环境已有数据不会因文档或副本整理而清理。

## 1. 登录、导航与权限

- 注册后显式登录，客户直接进入智能客服，无姓名/问题类型/订单金额的咨询表单。
- 客户端仅客户，管理员进入客户页面应回到后台；跨角色业务 API 返回 403。
- 商户左侧一级导航仅总览、管理、Agent；管理下为商品管理、客户管理、项目设置、提问与路由记录；客户管理下为聊天管理、订单管理、售后处理；Agent 下为 Agent运行、知识库、效果分析。
- 管理员从“我的账号”仅修改自己的名称/密码；不提供操作客户或其他管理员的入口。跨账号修改由服务端拒绝。
- 将窗口缩到手机宽度，导航能展开、滚动、折叠，不横向撑出。

## 2. 商品与购物闭环

1. 商户上架商品，填写名称、图片、描述、分类、价格和库存；图片支持不超过 2MB 的 PNG/JPEG/WebP。
2. 客户浏览、分类、搜索与价格排序，查看商品后填写数量和收货地址下单。
3. 我的订单中查看待支付订单并支付，检查已支付状态及交易流水。本项目不处理真实资金。
4. 商户订单管理应展示全部订单，不依赖是否存在售后咨询。依次发货、推进运输、确认送达，客户确认签收。
5. 未支付订单取消后释放库存；重复支付不重复记账；已下单金额不随商户改价变化；下架和缺货商品不能新下单。
6. 展开订单进度、处理时间线和交易流水，核对状态顺序及记录。

## 3. 在售商品与连续咨询

- 新对话问“商城有哪些商品”，答复应使用实际已上架商品，不虚构目录。
- 用商户自定义名称追问“是什么”“介绍一下”，继续问“它的规格是什么”；应保留最近商品主题，不要求必须命中售后政策文档。
- 已记录的事实如实回答；缺少具体资料时简短澄清，不编造成分、用途、库存或补货日期，不把内部防编造规则当作客服话术。
- 模糊指代或多个候选时先确认商品；明确改问别的商品则切换，不将所有旧商品混在一起。
- 价格、库存和上新计划来自业务记录，不以模型常识替代；目前没有实时补货计划字段。
- 普通连续咨询可超过十轮，不因轮数自动转人工。范围外通用问答引导回电商服务，不提供编程教学等内容。

## 4. 订单、物流与人工边界

从“我的订单”咨询此订单，或在聊天中提供自己的订单编号，答复应与当前订单状态一致。客户不能借别人的订单号查看其金额、地址或物流。

转人工条件保留：退款及资金操作、运输天数严格超过预计送达天数、明确要求人工、安全风险、质检耗尽或流程异常。普通商品资料缺失、普通优惠未知和对话轮数增加本身不触发人工。

人工接管后允许客户继续补充，机器人不持续抢答。管理员从聊天管理待人工筛选跟进；实际售后也可从售后处理打开。发送回复仍为处理中，只有客户确认“问题已解决”才关闭。

## 5. 聊天与售后归类

普通选购、商品详情和价格咨询属于普通聊天；主动要求人工也不自动变成售后。实际退款、退换货、破损和订单异常才进入售后处理。订单管理展示全部商城订单，聊天/售后列表不是订单全量视图。

## 6. 知识库、FAQ 与优惠

商户手动增加 FAQ，填写标题、答案和分类；打开文档后停用，再检索不应召回；重新启用恢复。停用不改写旧引用。

优惠券、折扣和促销属于电商范围。可靠命中已启用、适用的商家优惠 FAQ 时按文档说明并保留来源；没有可靠资料则说明暂时无法查询，不编造金额、规则、领取入口或用户已领券的状态。当前未接实时领券/核销系统，描述规则不等于执行发券。

## 7. 人工回复与客户反馈

1. 后台同一对话发送短回复和长多行回复，客服气泡及头像右边缘一致；客户消息在左侧。390px 下长连续字符也应换行。
2. 客户点击“评价本次对话”，选择评分、填写留言并提交“仍需帮助”；后台详情对话区域底部“客户反馈”应显示结果、评分、原留言和提交时间。
3. 后台沿用 3 秒轮询，无需重新运行 Agent。客户继续追问、人工继续回复、再次评价及刷新后，旧反馈仍在，最新在前。
4. 未评分、无留言或旧记录缺少时间时明确标注缺失，不补造数据。留言保留原意和换行，敏感信息仍脱敏；不混入客户聊天消息。

## 8. 提问与路由记录

每次客户消息保存独立记录，包括请求时间、工单号、路由、外部 API 尝试次数（含失败重试）、总/各步耗时、结果、降级与人工接管。可搜索并展开查看。

数据库本地读取、浏览器轮询和离线规则不计为外部模型/MCP API 请求。总耗时不含人工等待，并行节点耗时之和可能大于总耗时。未采集的旧字段不能补造。

工单按北京时间逐日原子编号，如 `26-10-16-1`；订单使用 `ORD-` 前缀。旧编号仅作历史查询，显示号与 UUID 不相同。

## 9. 自动验证

```bash
cd backend
python -m pytest -o addopts= -q
```

根目录运行隔离浏览器验证（需要 Python 3.11、Node 和 Playwright 浏览器）：

```bash
npm ci --prefix frontend
npm exec --prefix frontend -- playwright install chromium
node scripts/verify-commerce.cjs
```

设置 `RESOLVEAI_UI_PRODUCTION=1` 可验证正式构建，`RESOLVEAI_TEST_PYTHON` 可指定 Python。脚本使用独立 8200/3200 端口、临时 SQLite 和离线模型；会在临时库创建合成数据，不读取正常业务库或付费 Key。不要将其产生的截图、数据库或日志上传。

当前开发版 Windows / Linux 各 322 项后端测试通过；前端检查/生产构建、原双端流程、17 页 × 4 宽度共 68 组布局，以及新增人工回复/客户反馈同步回归通过。公开副本因清洁初始化增加的验证另见[指标汇总](RESULTS.md)。这些工程回归不能代替新增商城意图的真实模型评测或人工语义评分。
